# 채용공고 자동 발견 계획

## 1. 목적

사용자가 채용공고를 반복해서 복사해 붙여넣지 않아도 관심 직무의 신규 공고를 자동으로 발견하는 개인용 MVP의 수집 경계를 정의한다.

이 문서는 실행 코드를 정의하지 않는다. 어떤 경로를 허용하고, 각 경로에서 얻은 정보를 어디까지 사용할지 결정한다.

최종 확인일: 2026-09-13

## 2. 핵심 결정

공고 처리를 두 단계로 분리한다.

1. 발견: 새 공고의 제목, 회사, 링크, 게시 시점과 일부 조건을 찾아 후보 목록을 만든다.
2. 상세 수집: 주요 업무, 필수 조건과 우대 조건을 확보해 `JOB_POSTING_SCHEMA`로 변환한다.

발견에 성공했다고 상세 분석이 가능한 것은 아니다. 상세 정보의 공식 제공 경로가 없거나 이용 조건이 불명확하면 링크와 최소 메타데이터만 보관하고 `detail_status`를 `unavailable` 또는 `policy_review_required`로 기록한다.

## 3. 접근 방법 비교

| 방법 | 장점 | 한계 | 개인용 MVP 판단 |
| --- | --- | --- | --- |
| 공식 채용 API | 구조화 데이터와 명확한 호출 규칙을 기대할 수 있음 | 신청, 승인, 키 관리, 호출 제한이 있을 수 있음 | 상세 수집의 최우선 경로 |
| 공식 RSS | 키 없이 가볍게 신규 공고를 발견할 수 있음 | 항목 수와 필드가 제한되고 공고 전문이 없을 수 있음 | 첫 자동 발견 입력으로 사용 |
| 검색엔진 공식 API | 여러 기업 채용페이지와 ATS 링크를 한 번에 발견할 수 있음 | 검색 누락, 중복, 색인 지연이 있고 공고 전문을 보장하지 않음 | 기업 공식 페이지 발견용 보조 경로 |
| 기업 ATS 공개 API | 기업이 공개한 공고 목록과 상세 정보를 구조적으로 받을 수 있음 | 대상 기업 또는 ATS 식별자가 먼저 필요함 | 관심 기업 목록을 만든 뒤 우선 연결 |
| 사이트맵, JSON-LD | 기업 공식 페이지의 표준 메타데이터를 활용할 수 있음 | 사이트별 품질 차이가 크고 접근 정책 확인이 필요함 | 공식 API가 없을 때 제한적으로 검토 |
| 직접 HTML 크롤링 | API가 없는 페이지에서도 정보를 읽을 가능성이 있음 | 약관, robots 정책, 저작권, 구조 변경과 차단 위험이 큼 | 명시적으로 허용된 대상에만 최후 수단으로 검토 |

브라우저 자동화, 로그인 세션 재사용, 비공식 내부 API 호출, CAPTCHA 우회, 요청 제한 회피는 수집 경로로 사용하지 않는다.

### 외부 구현 참고 결정

2026-09-15 `NomaDamas/k-skill`의 `job-posting-match` 구현을 비교했다.

- 참고: <https://github.com/NomaDamas/k-skill/blob/main/docs/features/job-posting-match.md>
- 채택: 사용자 자료에서 1~3개의 집중 검색 표현 생성, 한 소스 실패 시 다른 허용 소스 계속 처리, 빈 결과에서 소스 갱신 여부 명시
- 미채택: 약관과 robots 정책을 별도로 확인하지 않은 잡코리아·사람인 검색 HTML 직접 수집
- 미채택: 상세 공고가 아닌 목록 요약의 키워드 일치를 0~100 적합도 점수로 표현

CareerBreak는 참고 구현의 코드를 복사하지 않는다. 검색 표현 생성과 실패 격리 원칙만 현재 구조에 맞게 적용하며, 공고 상세 조건과 사용자 증거의 비교 및 `gap`·`unknown` 구분을 유지한다.

## 4. 사이트별 접근 원칙

### 사람인

- 공식 채용공고 API를 우선한다.
- 현재 공식 안내상 이용 신청 승인과 access key 발급이 필요하고 일일 호출 제한이 있다.
- 개인용 이용 승인이 확인된 뒤 두 번째 수집 어댑터 후보로 검토한다.
- 승인 전에는 검색 결과 링크 발견 이상으로 확장하지 않는다.

공식 참고: <https://oapi.saramin.co.kr/guide/info>

### 잡코리아

- 공식 API 신청 페이지, 현재 제공 범위와 개인 프로젝트 승인 가능성을 먼저 확인한다.
- 승인이 되면 공식 응답만 사용한다.
- 승인이 없거나 현재 공식 제공 여부를 확인할 수 없으면 직접 상세 크롤링으로 대체하지 않는다.
- 초기 MVP 우선순위는 인크루트 RSS와 기업 ATS보다 낮게 둔다.

### 인크루트

- 공식 RSS를 신규 공고 발견과 1차 선별에 사용한다.
- RSS가 제공하지 않는 주요 업무와 자격 요건을 얻기 위해 상세 페이지를 자동 크롤링하지 않는다.
- 상세 내용은 해당 기업의 공식 채용페이지 또는 공식 ATS API가 별도로 발견될 때 그 경로를 사용한다.
- 개인회원 약관상 서비스 정보의 무단 복사·복제·제공이 제한되므로 RSS 메타데이터를 개인용 후보 관리 범위에서 최소한으로 저장한다.

공식 참고: <https://people.incruit.com/rss/rss.asp>, <https://help.incruit.com/docs/terms.asp>

### 원티드

- 공식적으로 허용된 API 또는 제휴 경로가 확인되기 전에는 상세 페이지 자동 수집 대상에서 제외한다.
- 검색엔진 공식 API에서 링크가 발견되면 제목, URL과 검색 시점만 후보로 저장하고 원티드 페이지 본문을 재수집하지 않는다.
- 비공식 내부 API나 접근 제한을 우회하는 방법은 사용하지 않는다.

### 기업 채용페이지

- 관심 기업의 공식 채용 URL을 먼저 식별한다.
- Greenhouse, Lever, Ashby처럼 공개 채용 API가 문서화된 ATS면 해당 공식 API를 우선한다.
- SmartRecruiters는 공개 공고 API의 현재 인증 조건을 대상 기업별로 확인한 뒤 사용한다.
- ATS API가 없으면 공식 RSS, 사이트맵과 `JobPosting` JSON-LD 제공 여부를 확인한다.
- 그 어떤 공식 구조도 없으면 약관과 robots 정책에서 자동 접근이 명시적으로 허용된 경우에만 낮은 빈도의 HTML 수집을 별도 검토한다.

공식 참고:

- Greenhouse Job Board API: <https://docs.greenhouse.io/job-board.html>
- Lever Postings API: <https://github.com/lever/postings-api>
- Ashby Job Postings API: <https://developers.ashbyhq.com/docs/public-job-posting-api>
- SmartRecruiters Posting API: <https://developers.smartrecruiters.com/docs/posting-api>

## 5. 검색엔진의 역할

검색엔진은 공고 본문 공급자가 아니라 공식 채용 URL과 ATS 유형을 발견하는 보조 수단으로 사용한다.

- 네이버 웹문서 검색 API를 국내 기업 채용페이지 발견 후보로 둔다.
- 검색 결과의 제목, 링크와 요약은 후보 판별에만 사용한다.
- 결과 링크의 상세 내용은 해당 사이트의 공식 제공 경로와 정책을 다시 확인한 뒤 가져온다.
- Google Custom Search JSON API는 신규 고객에게 제공되지 않으므로 신규 개인용 MVP의 기본 경로로 선택하지 않는다.

공식 참고:

- 네이버 웹문서 검색 API: <https://developers.naver.com/docs/serviceapi/search/web/web.md>
- Google Custom Search JSON API 상태: <https://developers.google.com/custom-search/v1/overview?hl=ko>

## 6. 첫 입력: 인크루트 IT 직군 RSS

첫 자동 발견 후보:

    https://www.incruit.com/rss/job.asp?occ1=150

2026-09-13 확인 결과 RSS 2.0 XML 형식으로 20개 항목을 반환했다.

항목에서 직접 확인된 필드:

- `title`: 회사명과 공고 제목
- `link`: 인크루트 공고 URL
- `description`: 회사명, 경력, 학력, 지역, 마감일을 포함한 HTML 조각
- `author`: 회사명
- `pubDate`: 게시 시점

RSS만으로 확인할 수 없는 핵심 필드:

- 주요 업무 전문
- 필수 조건 전문
- 우대 조건 전문
- 전체 기술 스택
- 정확한 고용 형태와 상세 근무 조건

따라서 RSS 항목만으로 최종 적합도 분석을 실행하지 않는다.

## 7. 발견 레코드 최소 필드

첫 구현은 `JOB_POSTING_SCHEMA`를 억지로 채우지 않고 별도의 발견 레코드를 만든다.

권장 최소 필드:

    discovery_id: "incruit-2609110004049"
    provider: "incruit"
    source_kind: "rss"
    external_id: "2609110004049"
    title: "비식별 예시 공고"
    company: "비식별 예시 기업"
    source_url: "https://job.incruit.com/..."
    published_at: "2026-09-11T21:09:01+09:00"
    experience_text: "신입"
    education_text: "무관"
    location_text: "경기"
    deadline_text: "09/16"
    discovered_at: "2026-09-13T09:00:00+09:00"
    content_scope: "metadata_only"
    detail_status: "unavailable"

실제 공고 문구 전문은 공개 저장소의 테스트 데이터에 넣지 않는다. 테스트에는 같은 구조의 비식별 합성 데이터를 사용한다.

## 8. 중복 제거 기준

1. RSS URL의 `job` 식별자를 `external_id`로 사용한다.
2. 같은 `provider`와 `external_id` 조합은 같은 발견 항목으로 본다.
3. 외부 ID가 없을 때만 정규화한 canonical URL의 해시를 대체 키로 사용한다.
4. 제목이나 회사명만으로는 중복을 확정하지 않는다.

## 9. 프로필 기반 후보 생성과 선별

검색 키워드, 제외 신호와 지역 조건을 사용자에게 다시 입력받지 않는다. Agent가 `USER_PROFILE_SCHEMA`의 목표 직무, 경력, 프로젝트, 기술, 행동 근거와 근무 선호에서 검색 계획을 도출한다.

현재 비식별 프로필에서 도출되는 직무 축:

| 우선순위 | 프로필 근거 | 검색 확장 예시 |
| --- | --- | --- |
| 1 | AI Automation / Workflow Engineer | AI 자동화, 업무 자동화, 워크플로 자동화, Automation Engineer |
| 2 | AI Solutions Engineer | AI 솔루션, Solutions Engineer, AI 엔지니어, LLM 응용 |
| 3 | Enterprise Solution / ITSM | 엔터프라이즈 솔루션, ITSM, 솔루션 엔지니어, 기술 컨설턴트 |
| 4 | Cloud / FinOps Automation | FinOps, 클라우드 자동화, 클라우드 비용 최적화 |
| 조건부 | Data Analyst / Analytics Automation | 데이터 자동화, Analytics Engineer, 분석 자동화 |

검색 확장어는 고정된 사용자 설정이 아니다. 목표 직무와 실제 공고 표현의 차이를 줄이기 위해 Agent가 만들고, 어떤 프로필 근거에서 생성됐는지 추적할 수 있어야 한다.

현재 프로필에서 도출되는 긍정 신호:

- Python을 사용한 자동화 구현
- REST API 연동
- LLM API 활용
- GitHub Actions 예약 실행과 로그 확인
- 웹개발 및 유지보수 경험
- 서버 비용 최적화 경험
- 문제 정의, 원인 탐색, PoC, 실제 개선으로 이어지는 업무

현재 프로필에서 도출되는 낮은 선호 신호:

- 반복 수작업이 중심인 역할
- 분석 결과를 정기 보고서로만 끝내는 역할
- 변화가 거의 없는 반복 운영 역할
- 목적과 결과가 불명확한 장기 반복 업무

낮은 선호 신호는 기본적으로 후보를 삭제하는 강제 제외 조건이 아니라 순위를 낮추는 근거로 사용한다. 제한된 제목만으로 역할의 실제 성격을 확정할 수 없기 때문이다.

현재 프로필에서 직접 확인되는 객관 조건:

- 선호 지역: 수도권
- 선호 고용 형태: 정규직

지역이 없거나 불명확한 공고는 버리지 않고 `unknown`으로 유지한다. 수도권 밖으로 명시된 공고는 낮은 우선순위로 표시한다. 재택근무 선호는 현재 프로필에 확정된 정보가 없으므로 묻거나 추정하지 않고 첫 발견 조건에서 제외한다.

RSS 메타데이터 단계에서는 다음만 수행한다.

1. 목표 직무 축과 제목의 관련성을 넓게 확인한다.
2. 프로필에서 도출한 긍정 신호가 제목 또는 제공 메타데이터에 있는지 확인한다.
3. 수도권과 정규직 조건은 확인 가능한 경우에만 반영한다.
4. 낮은 선호 신호는 삭제가 아니라 순위 조정에 사용한다.
5. 이미 본 공고인지 확인한다.

주요 업무와 자격 요건이 없으므로 이 단계에서는 `strong_match`, `gap` 또는 지원 추천을 만들지 않는다. 상세 공고가 확보된 뒤 `MATCHING_RULES`로 판정한다.

## 10. 운영 및 정책 안전장치

- 첫 실행 주기는 하루 1회로 제한한다.
- RSS의 갱신 빈도와 캐시 관련 응답 헤더를 존중한다.
- 요청 실패 시 짧은 횟수만 재시도하고 빈도를 늘려 우회하지 않는다.
- `403`, `429`, 인증 요구, CAPTCHA 또는 예상하지 못한 HTML 응답이 나오면 자동 수집을 중단한다.
- 이용약관, robots 정책 또는 공식 API 조건이 바뀌면 해당 공급자를 비활성화하고 재검토한다.
- 원문 전체가 필요하지 않은 발견 단계에서는 최소 메타데이터만 보관한다.
- 지원서 제출은 자동화하지 않고 사용자 확인을 필수로 한다.

## 11. 가장 작은 구현 순서

아직 코드를 작성하지 않으며, 구현을 시작할 때도 아래 순서로 한 단계씩 진행한다.

1. 비식별 합성 RSS 항목 1개와 기대 발견 레코드 1개를 만든다.
2. 두 데이터 사이의 필드 변환 규칙을 문서로 검토한다.
3. 합성 항목 1개만 변환하는 파서를 만든다.
4. 외부 ID 기반 중복 판정 1개를 추가한다.
5. 사용자 프로필에서 직무 축과 검색 확장어를 생성하는 규칙 1개를 추가한다.
6. 로컬 고정 데이터 테스트가 통과한 뒤 실제 RSS 읽기만 연결한다.
7. 결과를 로컬 파일로 확인한 뒤에만 하루 1회 예약 실행을 검토한다.
8. 별도 단계에서 관심 기업 1곳의 공식 ATS API를 연결해 상세 분석 가능성을 검증한다.

## 12. 첫 단계 완료 기준

- 사용자가 아무 공고도 복사하지 않아도 신규 후보가 생성된다.
- 같은 공고를 다시 읽어도 중복 후보가 생기지 않는다.
- 후보마다 원문 페이지 링크와 발견 시점이 남는다.
- 상세 정보가 없는 공고는 분석 가능한 것처럼 표시되지 않는다.
- 접근 제한을 우회하지 않는다.
- 실패 원인과 마지막 성공 시점을 로그에서 확인할 수 있다.
- 사용자가 별도 키워드를 작성하지 않아도 프로필 근거에서 검색 계획이 생성된다.
- 생성된 검색어와 순위 조정 근거를 사용자가 확인할 수 있다.
